## 2. 流式 outbox

### 2.1 问题

原实现每个 `stream.update` 都同步调用 `host.ui.command`。
每次调用都跨进程往返。
高频流式会放大会话插件的发布压力。

### 2.2 实现

新增 `plugins/session/stream_outbox.go`。

流程：

1. `updateStream` 只更新内存快照。
2. 增量进入 latest-value outbox。
3. 后台每约 33 ms 刷一次。
4. 同一会话的多条增量合并。
5. 内容与 reasoning 按顺序拼接。

合并帧增加可选字段：

```json
{
  "update_id": 100,
  "coalesced": true,
  "content_delta": "自上次发送后新增的完整文本",
  "reasoning_delta": "...",
  "status": "streaming"
}
```

保留语义：

- `reset=true` 时仍携带完整正文。
- 最终助手消息或 `turn_end` 到达时丢弃 pending。
- `clearStream` 同时清理内存快照与 outbox。
- 会话关闭或插件关闭时不再发送。

客户端处理：

- `coalesced=true` 时允许 `update_id` 跳变。
- 其他跳变仍触发 `session.state` resync。
- 最终助手消息已落地时忽略迟到的 stream 帧。
- 终态 Turn 忽略迟到帧并删除草稿。

### 2.3 实测

合成负载：

- 发送 100 次 `session.stream.update`。
- 每次正文递增 4 个字符。
- 最终正文 400 字符。

结果：

| 指标 | 结果 |
|---|---|
| 服务端发送帧数 | 31 |
| 合并帧数 | 30 |
| reset 帧数 | 1 |
| 最后 update_id | 100 |
| 收到正文长度 | 400 |
| 期望正文长度 | 400 |
| 正文一致 | 是 |

真实浏览器：

- 草稿长度 400。
- 草稿 `update_id` 为 100。
- 追加最终助手消息后，草稿清除。
- 最终消息正常显示。

真实流式 Turn 加 10 次刷新：

- 页面恢复选中会话。
- 状态保持“生成中”。
- `session.state` 最大 29,504 字节，最大 5 ms。
- Turn 最终 `completed`。

## 3. 失败 Turn 可见性

### 3.1 根因

聊天区只在过程消息前插入折叠头。
过程消息只包括 assistant 与 tool。
失败轮只有用户消息时没有折叠头。
因此状态和错误不可见。

### 3.2 实现

后端：

- `chatTurnInfoUI` 增加 `error`。
- `chatTurnUI` 增加 `error`。
- `chatTurnAppendUI` 增加 `error`。
- `turn_end.meta.error` 写入上述字段。

前端：

- 每个 Turn 记录最后一条消息。
- 没有过程消息的失败、取消或 max_steps Turn 追加状态行。
- 状态行显示轮次、状态和错误详情。
- 有过程消息的 Turn 在折叠头保留状态，错误放在 title。

新增 CSS：

- `.turn-status-row`
- `.turn-status-row.error`
- `.turn-status-row.cancelled`

### 3.3 Provider 错误

原错误是 `pipeline loop for llm.complete: pipeline_loop`。
原因是 provider 停止后，流水线只看到已访问的 consumer。

新增 `noActiveProviderError`：

- provider 路由存在且 active 时保留原错误。
- 路由缺失或 provider 非 active 时返回 `plugin_not_ready`。
- 消息为 `no active provider for llm.complete: plugin_not_ready`。

相关代码：

- `internal/host/pipeline.go`。
- `plugins/agent/turn.go` 仍负责写 `turn_end(error)`。

### 3.4 实测

操作：

1. 停止 `llm-openai`。
2. 在现有会话发送消息。
3. 等待失败。
4. 刷新页面。

结果：

- 状态行显示“第 2 轮 · 出错 · no active provider...”。
- 刷新后状态行仍存在。
- 错误不再只显示内部 `pipeline_loop`。
- 底部错误横幅仍会显示同一错误。

## 4. 默认模型跟随

### 4.1 实现

`applyCatalog` 记录上一次默认模型和当前选择。

规则：

- 用户没有手选过模型时，跟随新默认。
- 用户手选过其他模型时，保留手选值。
- 当前选择不在新目录中时，回退到默认。

相关代码：

- `plugins/session/ui/main.js` 的 `applyCatalog`。

### 4.2 实测

1. 设置页新增 `mimo-v2.6-flash-alt2`。
2. 将默认模型改为该值并保存。
3. 左侧“新会话模型”自动切换为 alt2。
4. 新建会话的模型为 alt2。
5. 已存在会话保持自己的模型。

测试后配置已恢复为 `mimo-v2.6-flash`。

## 5. 工作区选中一致性

### 5.1 旧行为

旧实现刻意保留跨工作区 pane。
这与 PRESSURE U8 的“无跨工作区会话”冲突。

### 5.2 新行为

`selectWorkspace` 现在同时协调选中会话：

1. 当前选中的会话属于新工作区时保持不变。
2. 否则恢复该工作区的 remembered session。
3. 没有 remembered session 时选择该工作区最新会话。
4. 工作区没有会话时清空选中。

内部调用：

- `setWorkspace` 只更新 registry。
- `selectSession`、`state`、`dock` 使用 `setWorkspace`。
- 用户切换使用 `selectWorkspace`。

其他工作区的 Tab 保留，但不进入当前 Chat Panes State。

### 5.3 测试

Go 测试更新为：

- `TestPublishPanesSelectsWorkspaceSession`。

- `TestStateReadFollowsRememberedWorkspaceSelection`。

## 6. 插件重启 resync

session 组件的 `resync()` 成功后清除旧错误提示。

## 8. 剩余风险

### 8.1 Host writer goroutine 未做

Host 读循环仍可能同步写回调用方。
插件持续消费 stdin 后可以恢复。
第三方插件不读 stdin 时仍可能拖住自己的读循环。

### 8.2 迟到 stream 帧

`clearStream` 丢弃 pending。
已经进入 `SendCommand` 的帧仍可能晚到。
前端通过“最终助手已落地”和终态 Turn 检查忽略它们。
仍需在长会话中继续观察。

### 8.3 大 State 预算

D2 State 仍可达到 5 MB 以上。
本次没有调整窗口常量或状态裁剪。
这部分仍是独立性能任务。

### 8.4 错误双显示

失败 Turn 现在同时有状态行和底部错误横幅。
后续可以决定是否只保留一种。

### 8.5 U8 行为变更

跨工作区 pane 不再保持选中。
打开其他工作区会话时仍会切换选中。
现有测试与文档已同步，但这是产品行为变化。
