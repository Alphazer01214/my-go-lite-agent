## 3. 问题与根因

### 3.1 I-08 运行期元数据不更新

现象：

- 新建会话发送消息后，标题仍是“新会话”，header 显示 `0 条消息`，Facts 为 `0`。
- 左侧列表已经显示“5 条记录”，聊天区已经出现用户消息和推理内容。
- 回合结束后才出现真实标题、消息数和 Facts。

根因：

- `plugins/session/ui/store.js` 的 `sendTurn()` 在 `started` 事件里只调用 `refreshSessions()`。
- `refreshSessions()` 更新左侧列表和 `fact_count`，但不更新 `state.meta`、`state.messages`、`state.facts`。
- header 和 Facts 面板读的是旧状态；只有 `loop.turn` 返回后才调用 `refreshCurrent()` 加载完整正文。
- 没有把 session 后端的实时计数传给 UI 的轻量通道。

### 3.2 I-09 日志量大且无轮转

实测旧日志：

| 指标 | 值 |
|---|---:|
| 文件大小 | 3,279,878 B |
| 总行数 | 25,172 |
| chunk 帧行数 | 22,500（约 89%） |
| 平均行长 | 128 B |

根因：

- `traceTo()` 对每条 Frame 都写一行，没有时间戳和级别。
- 流式 chunk 在 llm/loop 链路上被多次记录，单条 payload 虽被截到 200 B，但帧数量极大。
- 日志写 stderr，Host 没有文件 sink，也就没有轮转能力。

### 3.3 I-10 推理无上限、LLM 无超时

根因有三处：

- `plugins/llm-openai/plugin.go` 使用 `http.Client{}`，没有总超时。
- 浏览器调用的 context 是 `context.WithoutCancel`，上游卡住时只能等用户点停止。
- `buildChatRequest` 没有 `max_tokens`，也没有本地响应大小上限。
- UI 实时推理块默认展开，并且每收到一个 reasoning chunk 都强制 `open=true`；历史 reasoning 即使折叠也会立即解析完整 Markdown。

W1 的实测数据：单条助手消息 reasoning 60,887 字符，整轮 62,843 字符，耗时 12 分 03 秒。

### 3.4 I-11 错误文案原始且重复

根因：

- llm-openai 直接返回 `http.Do` 的错误，Host 包装成 `handler_error`，message 仍是 `dial tcp ... connectex ...`。
- agent 的 `finishTurn()` 只把 `cause.Error()` 写进 `turn_end.meta.error`，没有记录稳定错误码。
- UI 失败时 `reportError("本轮", error)` 同时渲染到聊天 banner 和左侧状态条，再加上聊天区 turn-status，形成重复。
- 失败回合虽然有“查看详情”，但标题和顶层提示仍暴露传输层细节。

### 3.5 I-12 dist 落后

`dist` 产物构建于 2026-11-05，版本 `31b5996-dirty`，当前 HEAD 是 `31b5996`，工作区还有未提交修改。
这是流程问题，不是运行时缺陷。修复完成后必须完整重建，否则测试对象不是当前源码。

### 3.6 shell 契约与 `__pycache__`

实际会话中模型两次把完整命令行放进 `command`：

```json
{"command": "python -c \"import time; time.sleep(6); print('x'*2000000)\""}
{"command": "D:\\Code\\Miniconda\\python.EXE -c \"import time; time.sleep(6); print('x'*2000000)\""}
```

工具契约要求 `command` 只是可执行文件，参数必须放在 `args[]`。
原描述只说明“不做 shell 解析”，没有明确禁止把参数塞进 `command`。

`test/` 已被 `.gitignore` 忽略，所以 `__pycache__` 不会进 Git，但会持续留在工作区。
上一份全量测试报告已经记录过同一问题，属于重复出现的验证副产物。

## 4. 修改思路

### 4.1 I-08 采用轻量轮询，不引入事件协议

没有让 agent 新增 `loop.progress` 事件，避免扩展事件契约和增加测试面。
选择：

1. session 后端在 store 里维护 `message_cnt`，随 append 和 recover 更新。
2. `session.info` 和 `session.list` 增加 `message_count` 字段。
3. UI 只对运行中的 Turn 每 2 秒调用 `session.info`，更新：
   - 当前会话标题；
   - header 消息数；
   - Facts 总数；
   - 左侧会话列表的 `fact_count`。
4. 新增轻量 `progress` 事件：chat 只更新 header，trace 只更新计数 badge，history 只重渲染列表，不触发聊天区全量 `render()`。
5. Turn 结束、失败或取消后停止轮询，继续走原有 `refreshCurrent()`。

边界：Facts 列表内容仍在回合结束后加载，运行中只保证计数增量，避免每 2 秒重读大会话文件。

### 4.2 I-09 把“全量帧日志”改成“摘要 + 可选文件轮转”

1. 所有日志行加时间戳和级别。
2. `LITEAGENT_TRACE` 控制帧日志：
   - `summary`（默认）：跳过 `method=chunk`；
   - `full`：保留全部帧；
   - `off`：关闭 trace。
3. 保留 200 B payload 截断；大帧不会整段落日志。
4. 新增可选轮转文件：
   - `LITEAGENT_LOG_FILE` 设置后才写文件；
   - 默认 `8 MiB × 3`；
   - 未设置时仍写 stderr，不改变默认部署方式。
5. 新增 `internal/logging`，用互斥锁保护写入和轮转。

### 4.3 I-10 用三层限制保护长推理

1. 请求总超时：默认 15 分钟，防止上游无限等待。
2. 流空闲超时：默认 2 分钟没有 chunk 就中断；持续输出 reasoning 的长任务不会被总时长立刻误杀。
3. 本地响应上限：默认 4 MiB，防止单次响应无限增长；`max_tokens` 作为模型可选配置，默认不下发，避免不兼容端点。
4. UI 推理展示：
   - 默认折叠；
   - summary 显示字符数和“生成中”；
   - 运行中最多写 32 KiB DOM，超出提示“显示已截断”；
   - 历史消息首次展开时才解析 Markdown，超过 32 KiB 先渲染前 32 KiB；
   - 显示已用时，超过 2 分钟提示“模型推理中，可停止后重试”；
   - 不再强制重新打开用户手动折叠的推理块。

### 4.4 I-11 统一错误码和展示入口

1. llm-openai 把连接失败、非 2xx、SSE 解析失败包装成 `llm_upstream_error`；超时用 `llm_timeout`；响应超限用 `llm_output_limit_exceeded`。
2. 传输细节只写 Host 日志，不进入返回给 UI 的 message。
3. agent 的 `turn_end.meta` 增加 `error_code`。
4. UI 增加错误码到中文文案的映射，显示“友好文案 + 错误码”；原始错误只放在“查看详情”里。
5. Turn 失败不再写 `state.error`，避免聊天 banner、左侧状态条和 turn-status 三处重复。
6. 未落库的失败也在聊天区草稿块内展示错误码、详情和重试。

### 4.5 shell 与 pycache

1. 在 `shell_execute` 的工具描述和 `command` 字段描述里明确：`command` 只能是一个可执行文件，参数必须逐项放进 `args[]`，并给出正确/错误示例。
2. 在 `execute` 入口增加运行时提示：`command` 含空白且不是存在的路径时，返回 `bad_arguments`，提示把参数放进 `args[]`。
3. `.gitignore` 增加 `__pycache__/` 和 `*.py[cod]`。
4. W1 流程增加验证后清理 `test/__pycache__` 和 `*.pyc` 的步骤。

## 8. 边界与后续

  - U1 的运行期标题、消息数、Facts 计数；
  - U4 的连接失败、刷新保留、重试不丢草稿；

- 本轮未执行 S9（2 小时、D4）、D4 长会话和完整 30 分钟日志轮转压测。
- 最新测试报告仍是 2026-11-03 的证据文档，本轮没有改写它的 P2 状态；复测后再更新报告状态。
